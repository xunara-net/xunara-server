# 设备确认接入失败：默认地址池排查与恢复

## What changed

设备地址分配耗尽返回可识别的 `state.ErrAddressExhausted`。浏览器设备审批、
v2 审批和预授权密钥接入均提供 `ADDRESS_POOL_EXHAUSTED`，不再把已知的
地址池冲突伪装成 `could not record the decision` 或笼统的存储故障。
Web 显示中文恢复建议，仍要求显式刷新，不自动重试批准。

## Why

2026-10-16，已有租户的历史导入记录保留了 `100.100.0.0/24`。这个范围已被
本项目的 `netspace.ClientReserved()` 排除，整池没有可用设备地址，即使该租户
设备数为零，也会分配失败。现行新租户分配已经跳过保留段，但不会替用户改写
历史网段；只用全新租户的夹具无法覆盖这种升级后配置。

## Compatibility impact

- TS2021、Noise、节点/机器密钥、注册字段和官方客户端轮询机制不变。
- 浏览器/v2 审批的此类已知冲突由 500 改为 409；机器注册仍使用标准
  `RegisterResponse.Error`，不改变协议的 HTTP 响应形状。
- 无迁移，不自动重编现有 IP、不重置计数器、不回退到入口租户或别的地址池。
- 附加 IPv4 池用于手动选择设备 IP；新增设备仍从默认池自动分配。

## Security impact

分配、授权决定、单次密钥消耗、必需审计及通知版本仍在同一事务内。
地址耗尽不能留下部分批准、已消耗密钥、额外设备或已发布通知。
服务端保留底层错误链供分类，但不向浏览器输出 SQL、密钥或内部路径。

## 排查和恢复

1. 先查看受限服务日志中的底层错误，区分地址耗尽、设备额度、权限、授权过期
   与实际存储故障；不要仅凭页面的一句 500 推断登录失败。
2. 只读核对该租户的 `address_configuration`、`tenant_plans`、
   `tenant_network_versions`、现有设备和其他租户预留，确认来源、实际网段及版本。
   零设备不代表地址池可用；也要检查保留段和 /31、/32 等小池的真实容量。
3. 修复前对套餐库及目标租户库做 SQLite 一致性备份，放入 root-only 目录。
   不直接编辑运行中的数据库，不重置用户密码，也不替用户批准设备。
4. 对需要恢复自动分配的历史租户，由平台管理员通过既有接口提交：

   ```text
   PATCH /api/platform/v1/organizations/<orgID>/plan
   Content-Type: application/json
   Authorization: 从受限存储读取的管理员凭据，仅放请求头
   ```

   ```json
   {"network_prefix": ""}
   ```

   这会重新选择不与其他租户及保留段冲突的自动块，更新期望与实际版本，并保留
   历史地址预留。不会升级套餐、转移设备或放行审批。自定义范围则由有 entitlement
   的所有者在「我的网络」调整；不要把所有地址耗尽都当作需要重分配的旧配置。
5. 只读验证两侧版本一致、其他租户未变、授权仍为原决定；已有设备保留原 IP。
   再由用户刷新并明确确认；链接已过期则在客户端重新发起登录，不延长旧授权。

## Tests

- 旧导入保留段 → 浏览器/v2 409 → 平台重新自动分配 → 原申请显式审批 →
  真实 Noise 注册 follow-up 成功；验证套餐、他租户、历史预留、幂等及原机器身份。
- IPv4/IPv6 耗尽均回滚单次接入密钥、节点、审计和通知，修复后可用原密钥重试。
- SQLite 与内存存储返回同一类型化错误，禁止自动分配到保留段或偷偷换池。
- Web 单测覆盖中文错误分类；浏览器夹具的 409 注入覆盖提示、禁用连续提交、
  不伪造成功及显式刷新。此注入不冒充生产实际设备审批。
